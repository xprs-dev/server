XPRS server

A station for your home: one program on a Linux machine, reachable from anywhere, with a name of its own under xprs.dev.

The XPRS server is a station that runs without a screen. It is a Reticulum node other stations and apps connect to, bridges the devices on your own network, keeps a public archive for other stations, and serves the XPRS web chat so anybody with a browser can talk to the network, no app needed.

This page takes you through three things, in order:

  1. Install it on a Linux machine. Ten minutes.
  2. Open it to the internet on your home router, so people outside your home can reach it.
  3. Get its name, yourcallsign.xprs.dev. This happens by itself once step 2 works.

What you need

  • A Linux machine that stays on, with systemd (Debian, Ubuntu, Raspberry Pi OS and most others). A Raspberry Pi 4 or 5 with the 64-bit Raspberry Pi OS is plenty: the server uses less than 200 MB of memory.
  • The ready-made program is for 64-bit ARM (a Raspberry Pi with a 64-bit system). On a PC (x86-64) build it from source, see the README.
  • Version 0.4.0 or later for the name under xprs.dev and for automatic updates.
  • A cable or WiFi connection to your home router, and the router's password, for part 2.

Install

  1. Download the program from the latest release and check it arrived whole:

    wget https://github.com/xprs-dev/server/releases/latest/download/xprs-server-linux-arm64
wget https://github.com/xprs-dev/server/releases/latest/download/xprs-server-linux-arm64.sha256
sha256sum -c xprs-server-linux-arm64.sha256
chmod +x xprs-server-linux-arm64

  2. Install the one library it needs (Debian, Ubuntu, Raspberry Pi OS):

    sudo apt install libsqlite3-0

  3. Install it as a service that starts with the machine:

    sudo ./xprs-server-linux-arm64 install-service

    This copies the program to /opt/xprs-server, creates a system user xprs for it, writes a commented configuration file to /etc/xprs-server/config.yaml, keeps its data in /var/lib/xprs-server, and starts it on port 80. Nothing else is needed: the web page is inside the program.

  4. See that it runs:

    systemctl status xprs-server
journalctl -u xprs-server -f      # the log, live; Ctrl+C to leave

    The log says server: 0.4.0, X3ABCD web chat ready. X3ABCD is your station's callsign: it was made from the station's own key the first time it started, and it is how every other station knows it.

  5. Open the web chat from a phone or computer on the same network: http:// followed by the machine's address, for example http://192.168.1.50/. hostname -I on the machine prints its address.

Become its administrator

The first person who opens Administration from the menu (☰), on the station's own network, can claim it. From then on only that person changes its settings: who may post, how far messages travel, the look of the page, and whether it updates itself. Claim it before you open the station to the internet; a claim from the internet is refused anyway.

Reach it from the internet

At home, every device shares one internet address: the router's. When somebody outside types that address, the router receives the request and does not know which of your devices it is for, so it throws it away. That is NAT, and it is why your station works at home but nobody outside can open it.

The fix is a rule on the router: requests for ports 80, 443 and 4242 go to the station. It is called port forwarding (also port sharing, virtual server or NAT rule, depending on the router). For IPv6 there is no NAT, but the router's firewall still blocks incoming requests, and the same kind of rule lets them through.

Why these three ports:

  • 443 is HTTPS, what browsers use for the web chat.
  • 80 is plain HTTP, which the certificate authority (Let's Encrypt) uses to check that the name really leads to your station before it issues a certificate.
  • 4242 is the station's Reticulum node: other XPRS stations, the XPRS app and any Reticulum program connect to the network through it. The same port also speaks XPRS as plain text.

Nothing else on the machine becomes reachable: only these three ports, only to the station.

Step 1. What kind of connection do you have?

Before changing anything, find out whether your router has a public IPv4 address of its own. Many cable and fibre providers share one IPv4 address among many customers (called CGNAT or DS-Lite), and then no rule on your router can bring IPv4 visitors in.

  1. Look up the internet address on the router's overview page (FRITZ!Box: Overview, the line Internet; other routers: Status, WAN).
  2. On the station, ask what the internet sees: 
    curl -4 https://api.ipify.org; echo
What you seeWhat it means
Both addresses are the sameA public IPv4 address. Port forwarding works. Go on.
The router shows 100.64.x.x to 100.127.x.x, or 10.x.x.x, and the station shows something elseCGNAT: IPv4 forwarding cannot work. Read No public IPv4 address.
The router shows no IPv4 address, or says DS-LiteDS-Lite: only IPv6 comes in. Read No public IPv4 address.

The station's log says the same thing in its own words. A few minutes after it starts:

public name: public addresses 178.202.105.29, 2a02:908:2616:da20:2ecf:67ff:fe14:d505

Step 2. Give the station a fixed address at home

The router hands out home addresses (192.168.x.x) as devices come and go. A forwarding rule points at one address, so the station must keep it. In the router's list of devices (Home Network, LAN, DHCP), find the station and tick always assign the same IPv4 address (also called DHCP reservation or static lease). The station's IPv6 address already stays the same on its own.

Step 3. Open ports 80 and 443

Make three rules, one per port. Every router asks for the same few things:

Or let the station ask. The station asks the router by itself (UPnP) to open ports 80, 443 and 4242. Most routers refuse unless you allow it for that one device; on a FRITZ!Box it is the tick Permit independent port sharing for this device. A rule you make by hand works just as well, and many people prefer it.

FRITZ!Box, step by step

Menu names from FRITZ!OS 7.5 and later; older versions word some of them differently.

  1. Open http://fritz.box and log in.
  2. Home Network → Network → the pencil next to the station → tick Always assign this network device the same IPv4 address → Apply.
  3. Internet → Permit Access → Port Sharing → Add Device for Sharing → choose the station under Device.
  4. New Sharing → Port sharing → application HTTP server (port 80). Tick Enable sharing for IPv4 and Enable sharing for IPv6 → OK.
  5. New Sharing again → Port sharing → application HTTPS server (port 443), both ticks → OK.
  6. New Sharing once more → Port sharing → application Other application, name XPRS, protocol TCP, port to device 4242 through 4242, port requested externally 4242, both ticks → OK.
  7. Apply. The device's line now lists three shares, for IPv4 and IPv6.

Instead of steps 4 and 5 you can tick Permit independent port sharing for this device and let the station open the ports itself.

Step 4. The firewall on the station itself

Raspberry Pi OS, Debian and Ubuntu let everything in by default. If you turned on a firewall on the machine, allow the same ports there:

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw allow 4242/tcp

Step 5. Check it from outside

The station tests itself from the internet every few minutes after a change, and backs off when a test fails (from 15 minutes up to 6 hours), so a restart makes it look at once:

sudo systemctl restart xprs-server
journalctl -u xprs-server -f | grep "public name"

Within a few minutes you want these lines:

public name: x3abcd.xprs.dev is reachable on port 80
public name: x3abcd.xprs.dev is reachable on port 443
public name: certificate for x3abcd.xprs.dev, ... until 2027-02-06
public name: web chat at https://x3abcd.xprs.dev/

For port 4242 the names keeper calls your station back from the internet each time the station claims its name, half-hourly until it works:

names: the keeper reached this station on port 4242 at 178.202.105.29
server: Reticulum node reachable at x3abcd.xprs.dev (announced as dial:)

Then open the address on a phone with WiFi switched off, so the test really comes from outside: many routers cannot reach their own public address from inside your home.

The web page shows the same thing: menu → Station lists Reachable at with the links that work, Not reachable yet with those still waiting for the router, and under Reticulum node whether port 4242 is reachable from the internet.

A Reticulum node

Every XPRS server is a Reticulum transport node on TCP port 4242, for IPv4 and IPv6. It keeps connections to the public Reticulum hubs on its own, and once port 4242 is open on your router it is an entry point for others too: XPRS apps, other XPRS stations, and any Reticulum program (Sideband, NomadNet, rnsd).

The station does not just assume it is reachable. When it claims its name, the names keeper connects back to it on port 4242 from the internet and sends a ping, which must come back signed by your station's key. Only then does the station announce its address to the network (dial:), so other stations and apps find your node by its callsign; if a later test fails, it stops announcing it.

To connect a Reticulum program to your station, add an interface to its configuration (~/.reticulum/config):

[[XPRS station]]
  type = TCPClientInterface
  enabled = yes
  target_host = x3abcd.xprs.dev
  target_port = 4242

The port is fixed by the XPRS specification: it is the port Reticulum hubs already use, and the same port speaks XPRS as plain text (one packet per line), told apart by the first byte. Change it only if you know why (rns_port in the configuration); the router rule must then use the same number, and the name's automatic test still looks at 4242.

Your name at xprs.dev

Your router's internet address can change, after a reconnect or whenever your provider decides. A name does not. Every XPRS station can have <callsign>.xprs.dev, for example x3abcd.xprs.dev, with nothing to register: no account, no form, no e-mail.

How it works

  1. The station's callsign is made from its own key, so the station can prove the callsign is its own by signing with that key.
  2. It asks the names keeper at names.xprs.dev for a challenge, signs a claim naming its public address, and sends it from that address. The keeper checks the signature, that the callsign belongs to the key, and that the request really came from the address named, and only then writes x3abcd.xprs.dev into DNS.
  3. The station tests the name from outside, gets a certificate for it from Let's Encrypt, and from then on publishes https://x3abcd.xprs.dev/ as its address: in the Station view, and to every other station.
  4. When the address changes, the station notices within 15 minutes and claims again. It also renews the claim every week.

All of it is automatic in version 0.4.0 and later; there is nothing to turn on. It needs exactly what part 2 set up: the station reachable on ports 80 and 443 from the internet.

The name stays yours

A callsign is short, so somebody could make another key that happens to give the same callsign. That is why a name belongs to the first key that claimed it, for at least six months after that key's last claim. A running station claims every week, so it keeps its name for as long as it runs. Only a station that has been silent for six months loses it. A claim from any other key meanwhile is refused with held by another key.

Choosing not to

Put names_keeper: "" in /etc/xprs-server/config.yaml and restart. The station then keeps only the nip.io names made from its address (178-202-105-29.nip.io), which also get a certificate and work, but change when the address does.

When something does not work

Everything the station tries is in its log:

journalctl -u xprs-server --since "1 hour ago" | grep -E "public name|names"
The log saysWhat to do
... is not reachable on port 80The router does not forward port 80 to the station yet, or forwards it to the wrong address. Check step 2 and step 3, then restart the station.
port 443 is closed, so no HTTPS yetPort 80 works, 443 does not. Add the second rule.
router refused IPv4 port 80: UPnP ...Harmless when you made the rules by hand. Otherwise allow the device to open ports itself (step 3).
the keeper sees A, not B; no claimYour connection to the internet does not leave from the address the station found: a VPN or a proxy on the machine, or two internet lines. Switch the VPN off for the station.
held by another key until ...Another station holds that callsign's name. Your station still works under its nip.io name. If it is your own old station whose key you lost, see Backup and moving.
not reachable on tcp 4242 from outside; no dial: announced, or Reticulum node: not reachable on the Station viewThe web works but port 4242 does not reach the station: add the third rule (step 3). The station asks again within half an hour, or at once after sudo systemctl restart xprs-server.
no public address foundThe machine has no internet connection, or DNS does not work on it.
It works from home but not from the phone on mobile dataTest again a few minutes later; the station tests itself every 15 minutes. If the log says reachable and the phone still fails, the phone's network may have no IPv6 while only IPv6 is open: open IPv4 too.

The station's own address and settings, from the machine:

xprs-server print-config --config /etc/xprs-server/config.yaml

No public IPv4 address (CGNAT, DS-Lite)

If step 1 showed that your provider shares your IPv4 address with others, IPv4 visitors can never reach you, whatever the router says. You still have choices:

  • Use IPv6. Your station has a public IPv6 address of its own. Make the IPv6 half of the rules in step 3; the station then gets its name with an IPv6 record. Every visitor whose own connection has IPv6 reaches it: most mobile networks and many home connections do, not all.
  • Ask your provider for a public IPv4 address. Many give one on request, often free (it may be called dual stack or public IPv4).
  • Leave it closed. The station still works fully as a station: it connects out to the XPRS network over the internet, carries messages, archives, and serves the web chat on your own network. Only visitors from outside cannot open it.

Updates

Every six hours the station looks for a newer stable release on GitHub. It installs one by itself after checking its digest, restarts, and goes back to the previous version if the new one does not start. You can switch this off in Administration → Updates, or with auto_update: off in the configuration file. By hand:

xprs-server --version
sudo xprs-server update --dry-run     # what is on GitHub, change nothing
sudo xprs-server update               # install it now

Backup and moving

The station's identity (its key, so its callsign and its name) and its archive live in /var/lib/xprs-server. Keep a copy of that folder somewhere safe:

sudo systemctl stop xprs-server
sudo tar czf xprs-station-backup.tgz -C /var/lib xprs-server
sudo systemctl start xprs-server

To move to another machine, install there as above, stop the service, put the folder back in /var/lib/xprs-server (owned by the user xprs) and start it. Same key, same callsign, same name: the new machine claims it at once from its own address.

A lost key cannot be recovered: the station comes back with a new callsign and gets a new name. The old name returns to the pool six months after its last claim. If you need it sooner, ask the names keeper's operator on the issue tracker.
